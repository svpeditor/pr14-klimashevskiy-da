# DECISIONS.md

## Вариант

Номер варианта: 4 (две последние цифры зачетки 25Т0859: 59 mod 8 + 1 = 4).

Изменяемый аспект: граница KPI, параметр 25.
Как применен параметр: в правиле граница KPI равна 80 %, и 80.00 уже относится к повышенной ставке.
Если поставить границу 25 %, повышенную премию получал бы сотрудник, выполнивший план на четверть, это
противоречит смыслу премии. Поэтому 25 применено как модификатор: 80 % увеличено на 25 %,
80 * 125 / 100 = 100 %. Повышенная ставка теперь только за полное выполнение плана.
Правило, которое реализовано: KPI от 100.00 включительно - ставка 15 %, ниже 100 - 5 %. 99.99 - 5 %,
100.00 - 15 %, 80.00 по варианту теперь 5 %.

Где сосредоточено: константы BonusCalculator.BASE_KPI_BOUNDARY = 80 и KPI_MODIFIER_PERCENT = 25, из них
считается KPI_BOUNDARY = 100. KPI_BOUNDARY использует только calculate.

## Формализованные правила расчета премии

Перед тестами я записал, как должен работать расчет:
1. Оклад, KPI и стаж не могут быть отрицательными, рейтинг только от 1 до 5, иначе IllegalArgumentException.
2. Базовая ставка 5 %, при KPI не ниже границы 15 % (в базе граница 80, по варианту 100).
3. Рейтинг 5 добавляет 5 %.
4. Стаж больше 5 лет (6 и больше) добавляет 2 %.
5. Премия = оклад * ставка, при окладе 0 премия 0.

## Найденные дефекты

Тесты написаны до исправления кода. На исходном BonusCalculator mvn test дал 18 тестов, из них 8 упали:
- отрицательный оклад давал 0 вместо ошибки - negativeSalaryMustBeRejected
- отрицательный KPI принимался и давал 5 % - negativeKpiMustBeRejected (строка 100000;-1;4;2 из sample.csv)
- рейтинг 0, -1 и 6 принимался - ratingOutOfRangeMustBeRejected (3 запуска)
- отрицательный стаж принимался - negativeYearsMustBeRejected
- KPI ровно 80.00 попадал в обычную ставку из-за > 80 - boundaryAtEightyPercent и вторая строка bonusTable

После исправления все 18 тестов прошли. После варианта тестов стало 20 (добавлены проверка, что 80.00 теперь
обычная ставка, и строка 80.00 в таблице), все 20 проходят.

## Решение 1. Проверка входных данных вынесена в private метод validate

Формулировка: первой строкой calculate вызывается validate(p), он бросает IllegalArgumentException для null,
отрицательного оклада, KPI, стажа и рейтинга вне 1..5. Сам расчет ставки остался теми же тремя строками,
что и в исходном классе.

Альтернатива: оставить if (p.salary() < 0) return 0 и дописать такие же return 0 для остальных полей.

Обоснование: премия 0 для неверных данных выглядит как настоящий результат, ошибку никто не заметит.
Исключение сразу показывает, что данные неверные. Класс не переписан целиком: заменена одна строка return 0
на вызов validate и знак > на >=.

## Решение 2. Граница KPI в константе и сравнение >=

Формулировка: p.kpiPercent() >= KPI_BOUNDARY вместо p.kpiPercent() > 80.

Альтернатива: оставить число в условии и поменять только знак.

Обоснование: правило говорит, что 79.99 и 80.00 относятся к разным правилам, значит сама граница входит
в повышенную ставку, нужен >=. Константа понадобилась для варианта: граница поменялась в одном месте,
а тесты границы поменялись вместе с требованием.

## Собственные формулировки

### Какая проверка защищает от наиболее вероятной ошибки входных данных

Самая вероятная ошибка - отрицательное число в выгрузке (как -1 в sample.csv) или опечатка в рейтинге.
Ее ловит private метод validate в BonusCalculator, который вызывается первой строкой calculate. Раньше
отрицательный KPI тихо давал 5 %, теперь расчет не выполняется и видно сообщение с причиной.

### Какой метод или класс содержит ключевое бизнес-правило и почему

Ключевое правило - выбор ставки по границе KPI. Оно в методе calculate, строка
rate = p.kpiPercent() >= KPI_BOUNDARY ? 0.15 : 0.05. Правило осталось в самом калькуляторе, потому что это
его единственная задача, а тесты проверяют его снаружи через публичный метод.

### Как Activity-диаграмма отражает участок кода

Диаграмма описывает, как я работал. Блок A1 "Выделить граничные случаи" - это список границ, по которому
написаны тесты: 99.99 и 100.00, стаж 5 и 6, нули, отрицательные значения. "Тест падает ожидаемо" - первый
запуск mvn test с 8 упавшими тестами. "Исправить минимальный участок" - замена return 0 на validate(p) и > на >=.
"Все тесты зеленые" - запуск после исправления, BUILD SUCCESS.

### Какое изменение требования затронет минимум классов

Изменение границы KPI меняет константы в BonusCalculator и тесты границы в BonusCalculatorTest, больше ничего.
Изменение ставок или надбавок тоже меняет одну строку calculate и ожидаемые значения в тестах.

## Фрагмент кода для анализа

if (kpiPercent > 80) { ... } не включает саму границу: при KPI ровно 80.00 условие ложно, и сотрудник получает
обычную ставку, хотя по правилу 80.00 относится к повышенной. Такой дефект не виден на типовых значениях
вроде 90 или 70, его ловит только тест прямо на границе, у меня это boundaryAtEightyPercent, который упал
на исходном коде. Исправление - знак >= и граница в константе KPI_BOUNDARY, по варианту она стала 100.
